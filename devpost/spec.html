Familien-Einkaufsplaner

Der Bauplan: TypeScript-Monorepo, Fastify + React, SQLite, ein LLM-Aufruf mit fester Antwortstruktur — und eine saubere Naht für den späteren Angebot-Fetcher.

Verbindliches Dokument: devpost/spec.md · Basis: devpost/prd.md (genehmigt)

Wie es funktioniert — in einem Absatz

Du öffnest die Seite → der Browser lädt eine React-App → sie fragt den Fastify-Server per REST/JSON → der liest und schreibt eine SQLite-Datei auf einem Docker-Mount. Beim „Plan erstellen“ sammelt der Server vier Dinge — Personen mit Einschränkungen, Wochenmuster, Rezept-Pool, neueste Angebots-Momentaufnahme — und gibt sie einem einzelnen Claude-Aufruf mit fester Antwortstruktur mit. Die Antwort wird gegen ein Schema geprüft (max. 2 kontrollierte Retries), erst dann gespeichert.

Die Einkaufsliste rechnet der Server selbst aus — Zutaten aggregiert, Preise aus den Angeboten, kcal aus einem Nährwert-Werkblatt. Das LLM wählt und kombiniert; rechnen tut der Rechner.

Komponenten — jede mit ihrem PRD-Zuhause

Frontend apps/web — die vier Oberflächenprd.md › Screens and Layout›
Hauptbildschirm (Ladenwahl, „basiert auf N Angeboten“, Next-Meal-Hero, Wochenstreifen, Listen-CTA), Tagesdetail, Einkaufsliste, Onboarding/Einstellungen. Theming über CSS-Custom-Properties: Light/Dark/System, große-Schrift-Option, reduced-motion, Pastell-Paare pro Person am Profil-Umschalter. Kein CSS-Framework.
Backend apps/api — Fastify-RESTprd.md › Features and Behavior›
Endpoints: GET /api/state, POST /api/household/demo, POST /api/persons, PATCH /api/persons/:id, POST /api/plan/generate, POST /api/plan/events, POST /api/plan/exemptions, PATCH /api/shopping-list/:itemId, GET /api/offers/latest, POST /api/offers/refresh. Alle Antworten typisiert über packages/shared.
Der Kopf llm/planner.ts + context-contract.tsprd.md › Wochenplan›
Kontext sammeln → PII-Filter: Personen werden pseudonymisiert (GUID statt Name, Rollenklasse statt Alter, Constraint-Tags + reine Zahlen; Namen, Haushaltsname, Beruf-Freitext verlassen den Server nie) → Claude mit fester Antwortstruktur → zod-Validierung → max. 2 kontrollierte Retries mit Fehlerkontext → Plan re-pseudonymisiert zurückübersetzt und persistiert. Aufgaben (Lerner-Entscheidung): Rezeptauswahl, Allergie-/Constraint-Check, Wochenplanzusammenstellung, Portionierung. Um die offene Frage „Kerne oder voller Kontext": Start mit dem Minimal-Kern + Miss-Log; Qualitätsverlust wird durch kontrolliertes Erweitern des Vertrags beantwortet, nie durch PII-Nachschub.
Der Rechner domain/aggregation.tsprd.md › Einkaufsliste›
Deterministisch: Zutaten der Wochenrezepte aggregieren (Gramm summieren, Stück zählen: „2× Zucchini“), Preise + Angebots-Badges aus dem Snapshot, Gruppierung nach Abteilung, kcal aus data/nutrition.json. Hier liegen die Vitest-Tests — das „nachrechenbar“-Versprechen aus dem PRD.
Die Naht offers/store.ts + data/prd.md › Angebots-Basis›
OfferSource.latest() liefert den neuesten Snapshot aus data/offers/*.json (Datum im Dateinamen + fetchedAt/source im File), refresh() scannt erneut. Snapshots entstehen im Build: Agent überführt 20–30 reale Aktionen von den Lidl-/Aldi-Süd-Angebotsseiten in JSON — echte Daten, dokumentierte Herkunft. Später dockt der nächtliche Fetcher hier an.
Daten Rezept-Pool & Persistenzprd.md › Open Questions›
data/recipes.json: ~24 kuratierte discounter-typische Rezepte (Zutaten mit Grammatur, Tags vegetarisch/milchfrei/schnell, Kurz-Anleitung) — beantwortet die offene PRD-Frage. SQLite-Tabellen: household, person, week_plan (zod-gültiges JSON), list_item, event. Alles überlebt Neustart am Bind-Mount.

Wenn etwas bricht

LLM liefert Müll

zod fängt es → 2 Retries mit Fehlerkontext → klare Fehlermeldung; der bisherige Plan bleibt unangetastet.

Kein aktueller Snapshot

Offene Meldung mit Datum der letzten Lage + Option „trotzdem planen“; Plan wird als „ohne aktuelle Angebote“ markiert.

Claude-API langsam/weg

Ladeanzeige, Timeout-Meldung; Plan und Liste bleiben nutzbar — Liste ist ohne LLM neu berechenbar.

Bewusste Vereinfachungen

Vereinfacht Sechs Ersetzungen mit Begründung›
  • Datierte echte Snapshots statt Live-Scraper — die Daten sind echt, nur der Transport ist manuell; Fetcher dockt später an OfferSource.
  • Refresh beim Laden/Knopf statt nächtlichem Cron — Lerner-Idee, auf „nach erstem Deploy“ verschoben.
  • Voller Payload statt Delta-Protokoll — ein paar KB JSON.
  • SQLite statt Cloud-DB — ein Dienst weniger.
  • Profil-Umschalter statt Auth — aus dem PRD.
  • Nährwert-Tabelle statt LLM-Schätzung — nachrechenbar schlägt gefühlt.

Entscheidungen & Restpunkte

Dokumentiert Wer entschied was — und das eine echte Unbekannte›

Lerner-Entscheidungen: Docker + Mount; Monorepo; typisierte Endpunkte; LLM-Scope auf vier Aufgaben; PII-Minimierung am LLM-Aufruf (nur IDs/GUIDs, kein PII). Verworfene Lerner-Ideen: HTMX, GCP-DB, Protobuf/SignalR, nächtlicher Cron (verschoben), Delta-Protokoll.

Agent-Empfehlungen, bestätigt: TypeScript überall, Fastify, SQLite, REST+JSON, Snapshot-Strategie, Nährwert-Tabelle; Monorepo statt Zwei-Repos (auf explizite Nachfrage bekräftigt: geteilte Typen schlagen Repos-Grenzen).

Geklärtes Unbekanntes 1: Wie zuverlässig liefert das LLM validierbare Pläne? → Schema-Zwangsantwort + zod + begrenzte Retries + „letzter guter Plan bleibt“. Im Build: Test mit geflashter Invalid-Antwort.

Geklärtes Unbekanntes 2: „Kerne oder voller Kontext“ beim LLM-Aufruf? → Minimal-Kern pseudonymisiert starten + Miss-Log; Qualitätsverlust = kontrolliert Vertragsfeld ergänzen, nie PII-Nachschub. Beleg im Build: Planner-Testlauf mit/ohne Vertragsfelder.
